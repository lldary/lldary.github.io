Part 2: Implement a Simple BP

A prediction result of a BP can be 'taken' (represented by 1), which means the branch instruction should take the branch and jump to the branch target, or 'not taken' (represented by 0), which means the branch instruction should not branch. In this part, we will build a simple static branch predictor (simple_bp), which always predicts 'taken'.

ChampSim provides built-in branch predictors in the branch/ directory and modularizes branch predictors purely in C++. Adding a new branch predictor in ChampSim only requires creating a new folder with source files inside the branch/ directory and implementing a few interface functions.

Note

In ChampSim, core structures such as the Branch Target Buffer (BTB) and Return Address Stack (RAS) are handled by the main simulation framework. In this project, your implementation will mainly focus on predicting conditional branch outcomes inside your custom predictor module under branch/ (specifically implementing predict_branch() and last_branch_result()).

To create our simple branch predictor, let's create a new directory named simple_bp under the branch/ directory, and add simple_bp.cc and simple_bp.h inside branch/simple_bp/:

#include "msl/fwcounter.h"

  bool predict_branch(champsim::address ip);
  void last_branch_result(champsim::address ip, champsim::address branch_target, bool taken, uint8_t branch_type);

#endif

// branch/simple_bp/simple_bp.cc
#include "simple_bp.h"

// Predict whether a branch is taken (1) or not taken (0)
uint8_t simple_bp::predict_branch(uint64_t ip, uint64_t predicted_target, uint8_t always_taken, uint8_t branch_type) {
    // Always predict 'taken'
    return 1;

// Update predictor state after branch execution
void simple_bp::last_branch_result(champsim::address ip, champsim::address branch_target, bool taken, uint8_t branch_type) {
    // Static predictor does not update any state.

  • last_branch_result(): Called when the branch instruction is executed/committed and its actual outcome (taken) is known. You use this callback to update your prediction tables or history registers.

Part 3: Read Paper, Implement your own Perceptron BP

A Brief Introduction to 2-Bit Local BP and GShare Predictor

Before designing your own branch predictor, we first review two foundational dynamic branch predictors: the 2-bit local BP and the GShare predictor.

As shown in Fig (a) above, the 2-bit local BP contains a table of saturating counters. When a branch instruction is fetched, the BP indexes into the counter table using the instruction's PC. The BP predicts 'taken' if the counter value is 2 (10) or 3 (11), and 'not taken' if the counter value is 0 (00) or 1 (01). When the actual branch outcome is resolved, the corresponding counter in the table is updated: it is incremented by 1 (saturating at 3) if the actual outcome is 'taken', and decremented by 1 (saturating at 0) if 'not taken'.

However, the outcome of a branch is often strongly correlated with the outcomes of other recent branches. A local predictor that relies solely on a single branch's past behavior (like the 2-bit local BP) cannot capture these inter-branch correlations.

To leverage global branch history, the GShare predictor introduces a Global History Register (GHR), as shown in Fig (b) above. The GHR maintains a shift register where each bit represents the outcome of a recent conditional branch instruction (1 for taken, 0 for not taken). When a branch outcome is resolved, the GHR updates via a bitwise shift:

GHR = ((GHR << 1) | outcome) & GHR_MASK;

When indexing into the counter table, GShare XORs (hashes) the instruction's PC with the GHR. This hash ensures that global history is factored into table indexing, allowing the predictor to distinguish between different execution paths leading to the same branch.

A Brief Introduction to Perceptron BP

Now, we introduce the Perceptron Branch Predictor, originally proposed by Jiménez and Lin:

Citation

Jiménez, Daniel A. and Calvin Lin. “Dynamic branch prediction with perceptrons.” Proceedings HPCA Seventh International Symposium on High-Performance Computer Architecture (2001): 197-206.

Read the paper PDF

The perceptron BP replaces traditional 2-bit saturating counters with artificial perceptrons. A perceptron is represented as a vector of signed integer weights (w0​,w1​,…,wk​), where w0​ is a bias weight and w1​…wk​ correspond to the k bits in the GHR.

  1. Prediction: Instead of checking counter thresholds, the BP selects a perceptron using the branch PC and computes the dot product of its weight vector and the GHR (treating GHR bits 1 as +1 and 0 as −1):

y=w0​+i=1∑k​wi​×GHR[i]

If y≥0, the BP predicts 'taken' (1); otherwise, it predicts 'not taken' (0).

  1. Training/Update: Once the actual branch outcome t∈{−1,+1} is known, the predictor trains the selected perceptron weights. A weight wi​ is incremented if the historical outcome matches t, and decremented if it differs. To avoid overtraining, training only occurs if:
  • The prediction was incorrect,
  • The absolute value of the dot product ∣y∣ is within a predefined threshold θ (∣y∣≤θ).

Note: As part of this lab, you are required to read the paper cited above and summarize its key design in your report.

Part 4: Crafting a Hard Trace Benchmark for Branch Prediction

In this part, you will flip your role from a hardware designer to a software/workload developer. You are required to design, compile, and generate a custom ChampSim trace that serves as a stress test for branch predictors.

Background & Objective

Standard benchmarks like sorting or matrix multiplication often exhibit regular loops and repetitive control flow patterns. However, real-world software—such as database indexing, cryptosystems, binary parsers, and graph analytics—contains complex, data-dependent, and highly unpredictable branch behavior.

Your goal is to write a C/C++ program featuring intricate control flow that maximizes branch prediction difficulty, compile it, and collect a trace file using ChampSim's trace collection tools.

Guidelines for Designing Unpredictable Workloads

To create a high-difficulty trace that forces frequent mispredictions across standard predictors, consider incorporating:

  • Data-Dependent Branches: Branches whose outcomes depend on unpredictable data (e.g., pseudo-random number generators, cryptographic hashes, or Collatz conjecture sequences).
  • Long-History Dependencies: Control flow patterns where branch outcomes correlate with events that happened beyond typical global history lengths (k>64).
  • Irregular Memory & Pointer Chasing: Unstructured graph traversals (e.g., BFS/DFS on sparse graphs, skip lists, or unbalanced tree searches).
  • High-Entropy Conditional Statements: Interleaved conditional logic that induces heavy aliasing (collisions) in branch target/predictor tables.

Appendix: Perceptron BP Method Brief Description

The overall structure of a perceptron BP is shown below:

The Select Entry step is to hash the PC. The hash can be XORing PC with the GHR or other methods. Each perceptron is a vector of weight [wi​]n​, and each weight is a signed integer. When predicts, the BP computes: y=w0​+i=1∑n​wi​xi​ where the w0​ is the bias, xi​ is the i-th bit of GHR (value '0' is regarded as '-1' when multiply). If y≥0, the prediction will be 'take', and vice versa. When the actual branch outcome is known, the perceptron that is used to predict this branch is trained with the following method:

if sign(y)=t or abs(y)≤θ

  for i in 0..n # also update bias

    wi​+=txi​

  end for

end if

where t is the actual outcome, set t=1 for 'taken' and t=−1 for 'not taken'. θ is the threshold.
