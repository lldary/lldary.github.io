Archlab ChampSim Project 3

Part 1: Data Cache Capacity Allocation and Associativity

Explore how data cache capacity, set mapping, associativity, and access latency affect performance in ChampSim. Keep the instruction cache (L1I) unchanged and organize L1D and L2C under an exact capacity budget. Your goal is to find the best configuration among those you test, and explain its performance using cache statistics and configured latencies.

Use the course ChampSim environment from Project 1.

1. Prepare the Workloads

Part 1 uses two synthetic teaching traces:

TraceRequired experimentPurpose
cache-capacity.champsimtrace.xzCapacity allocationReuse hot data while traversing a larger working set; investigate capacity and latency tradeoffs.
cache-conflict.champsimtrace.xzSets and associativityRepeatedly access blocks with matching page offsets; investigate mapping conflicts at fixed capacity.

Download both course-provided trace files from the PKU Disk into the ChampSim traces/ directory. Each contains 124M instructions, enough for the required 20M warmup followed by 100M measurement.

Keep the provided trace contents and simulation window identical across configurations.

Exact Capacity Budget

With 64 B cache lines:

Slevel​=sets×ways×64 B.

  • L1I: 64×8×64 B=32 KiB, fixed throughout.
  • L1D: 64×12×64 B=48 KiB.
  • L2C: 2048×16×64 B=2048 KiB.
  • Total: 2128 KiB=2,179,072 B.

Here, 1 KiB=1024 B. The budget counts data capacity, excluding tags and metadata. Every tested configuration must satisfy:

SL1D​+SL2C​=2096 KiB.

Controlled Parameters and Latencies

Only change L1D/L2C sets and ways as allowed by each experiment. Keep all L1I settings, the CPU, block size, MSHRs, queue sizes, tag/fill bandwidths, replacement policies, prefetchers, address translation, and DRAM settings unchanged. The explicit max_tag_check and max_fill values prevent bandwidth from changing automatically when sets change. You may change executable_name to distinguish binaries.

Do not override cache latency, hit_latency, or fill_latency. Let the course version compute them from the cache organization, and record the resulting hit/fill latencies for every configuration. The default calculation is in inc/cache_builder.h; for the baseline it gives L1D hit/fill 2/3 cycles and L2C 8/9 cycles.

Build and Run

./config.sh lab3_config.json
make -j $(nproc)
mkdir -p results

Run the baseline on both traces from the ChampSim root:

./bin/champsim_proj3_baseline --json results/baseline_capacity.json --warmup-instructions 20000000 --simulation-instructions 100000000 traces/cache-capacity.champsimtrace.xz > results/baseline_capacity.txt
./bin/champsim_proj3_baseline --json results/baseline_conflict.json --warmup-instructions 20000000 --simulation-instructions 100000000 traces/cache-conflict.champsimtrace.xz > results/baseline_conflict.txt

All final comparisons must use 20M warmup + 100M measurement. Check that the run completes and the final CPU statistics include at least 100M measured instructions.

For each modified configuration, you can save a separate JSON and use a distinct executable name. You can then re-run config.sh and make, run the corresponding binary, and save its stdout and JSON statistics under distinct result names.

Use cache-capacity.champsimtrace.xz. Compare at least three L1D/L2C capacity allocations under the exact budget. Keep L1I fixed. The following configurations are valid starting points:

You may test additional valid configurations and refine your choices based on measurements. Under this exact budget, ways may need to change along with capacity. Explain these coupled changes.

Address the following questions:

  • Which tested allocation achieves the highest IPC, and what supports that conclusion?
  • How do the hot working set and reuse pattern explain L1D misses and L2C accesses?
  • Does a lower miss rate always produce higher IPC? Account for the configured latencies.
  • Is there evidence that L2C capacity is insufficient?

4. Sets and Associativity Experiment

Use cache-conflict.champsimtrace.xz. Keep L1D capacity at 48 KiB, L2C at the full baseline configuration, and L1I unchanged. Compare at least three L1D organizations:

L1D setsL1D waysL1D capacity
128648 KiB
641248 KiB
322448 KiB

The set/way product must remain constant. Changing sets also changes address mapping; changing ways may change the default latency. Analyze both effects.

Address the following questions:

  • How can a working set smaller than the cache still cause frequent misses?
  • Which address bits select a set, and how do the trace's page offsets affect mapping?
  • Does increasing ways always improve performance when sets decrease at the same time?
  • Which comparison most clearly isolates mapping conflicts from latency changes?

Use workload structure, warmup, and measured counters to support a conflict-miss explanation. Ordinary miss counters do not directly classify misses as compulsory, capacity, or conflict misses.

5. Measurements, Analysis, and Deliverables

Use the final Region of Interest Statistics, excluding warmup. For these load-based traces, consistently use the LOAD rows of CPU 0's L1D and L2C:

MetricDefinition
IPCMeasured retired instructions / measured CPU cycles
Total cyclesCPU cycles from the same measurement window
Local LOAD miss rateCache LOAD MISS / cache LOAD ACCESS
LOAD MPKI1000 × cache LOAD MISS / measured retired instructions

Also retain LOAD ACCESS, MISS, and MISS_MERGE counts, and record cache sets, ways, capacities, MSHRs, and configured hit/fill latencies. Keep MISS and MISS_MERGE separate. L2C only sees requests that missed in L1D. Its local miss rate can rise simply because fewer requests reach it, so always read the rate together with the access count and MPKI.

If a cache has zero LOAD accesses, report its miss rate as N/A. If the text output does not list a cache at all, check the JSON: zero counters mean the cache was never accessed, while missing fields mean the run did not finish or the output is incomplete.

Deliverables

Submit the following in your report and source archive:

  1. Reproducible configurations: The baseline and every tested variant JSON, course ChampSim revision, build/run commands, and successful build/run evidence.
  2. Capacity allocation results: At least three allocations on cache-capacity, with IPC, cycles, L1D/L2C LOAD counts, miss rates, MPKI, and configured hit/fill latencies. Explain the best tested allocation using the measurements.
  3. Associativity results: At least three fixed-capacity L1D organizations on cache-conflict, with the same metrics. Explain the observed mapping conflicts and latency effects.
  4. Raw evidence: Original stdout and JSON statistics, plus the result tables in CSV form. Discuss unchanged or degraded performance when observed; an improvement is not required for every modification.

At minimum, run six simulations: three allocations on cache-capacity and three organizations on cache-conflict. The baseline must be run separately on each trace.
