Archlab ChampSim Project 3

Part 4: Cache-Aware Optimization of a Telemetry Analysis Program

Optimize a working telemetry analysis program while preserving its results. A device gateway stores normalized sensor readings in acquisition order. The offline program filters these readings through four processing stages and produces a health report for each group of devices. Your task is to make this computation faster on the fixed ChampSim platform by improving how it uses the cache hierarchy.

Part 4 contributes 6 points. Most points reward experimental design and analysis; performance is measured by the cycles required to complete the same task.

Download and extract the Part 4 starter package. It contains the original implementation, a student copy to optimize, the fixed arithmetic and checking driver, a ChampSim configuration, and a complete-ROI trace capture utility. Optimized implementations are not included.

The sixteen channels represent normalized deviations of measurements such as temperature, vibration, current, voltage, pressure and flow. All channels contribute to the output. The original implementation passes complete intermediate arrays between processing stages. It is functionally correct, but its processing order and intermediate working sets leave room for optimization.

Only this medium-sized input is used for the reported performance score. Small cases in the checker test correctness. Hidden correctness cases may change the data, seed and medium-sized dimensions, including incomplete device groups and block tails; the sixteen channels, four stages and four-point calculation remain fixed.

Exact Computation

Input acquisition order is [time][device][channel]:

input.data[(t * D + d) * 16 + c]

Let x[0] be the input. For stage s = 0, 1, 2, 3, compute the following for every device and channel at times t >= 3*(s+1):

weighted = x[s][t,d,c] + 2*x[s][t-1,d,c]
         + 3*x[s][t-2,d,c] + 4*x[s][t-3,d,c]
value = weighted / 10
limit = 2400 - 100*s + 50*(c % 4)
x[s+1][t,d,c] = clamp(value, -limit, limit)

Use signed 64-bit accumulation. Division is integer division toward zero, followed by clamping at every stage. The supplied condition() primitive already implements this short calculation; you do not need to derive a signal-processing algorithm.

The final valid time range is 12 <= t < T. Store every final filtered reading in:

output.filtered[((t - 12) * D + d) * 16 + c]

For each valid time, compute a device's risk as the sum of the absolute values of its sixteen final readings. Its alert threshold is:

threshold[d] = 600*16 + (19*d) % (400*16)

A device is in alert when its risk is strictly greater than this threshold. For each group of up to sixteen devices, produce the total risk, number of devices in alert, and maximum device risk. The last group uses its actual device count. Report layout is [t-12][group], with ceil(D/16) groups. summarize() supplies this computation.

Optimization Scope

Keep the input, all final filtered readings, and every report field unchanged. Preserve the per-stage weighted contributions, integer truncation and clamping, and the main O(stages * T * D * channels * history) computation. You may reorganize loops, change internal layouts, block the work, pack data, fuse compatible work and reuse loaded samples or intermediate values. Explain why your changes preserve the dependency order.

Keep all data-dependent computation, explicit preprocessing, intermediate initialization, copying and report construction inside analyze(). The input is read-only. Use single-threaded scalar C++ and the supplied compiler flags. Preserve the fixed headers, reference implementation, driver, ROI markers, tracer and hardware configuration. You may add your own helper files; add them only to the student executable's build dependencies and command, keeping the flags unchanged.

Prefix sums, running updates of window aggregates, FFT-based filtering, collapsing stages, skipping required contributions, changing the input or task size, and precomputed answers are outside this lab's optimization scope. Keeping original history samples for later reuse is allowed when each valid output still evaluates the prescribed contributions. Hidden output checks verify semantics; source review also checks the required computation structure. The grader uses the original course driver and reference files.

Build and Check

Use the Linux environment prepared in Lab 1. After extracting the archive:

cd part4-starter
make -j2
make check
./bin/telemetry_student --pattern demo --csv health-report.csv

make check compares every filtered reading and report field on multiple inputs. The demo exports a readable device-group report with quiet periods, transient spikes and sustained faults. It is separate from the official stress performance input.

The fixed build flags are:

-std=c++17 -O2 -fno-tree-vectorize -fno-tree-slp-vectorize
-fno-unroll-loops -fno-pie -no-pie -Wall -Wextra -Werror

The reference executable is built independently of student.cc. Each normal run verifies its complete output outside the measured region and prints JSON containing verified: true and a checksum. The checksum is for reproducibility; verification compares the actual arrays and report fields. Do not use native wall-clock time as the ChampSim performance result.

Measure the Complete Task

Optimizations can change dynamic instruction counts. Capture the complete call to the analysis function and compare the cycles needed to finish it. Use zero warmup and the original instruction length of each implementation's own ROI. The 20M + 100M prefetcher window from Parts 2 and 3 does not apply here.

The fixed driver places roi_begin and roi_end around the computation. Input generation, driver correctness checks and CSV export are outside this region. All work performed by the analysis function, including temporary allocation, initialization, packing and report construction, is measured.

Capture the reference and current student implementation:

python3 capture_trace.py --pin-root "$PIN_ROOT" \
    --tracer tracer/obj-intel64/champsim_tracer.so \
    --output traces/reference.champsimtrace.xz -- \
    ./bin/telemetry_reference --times 512 --devices 64 --seed 123 --pattern stress

python3 capture_trace.py --pin-root "$PIN_ROOT" \
    --tracer tracer/obj-intel64/champsim_tracer.so \
    --output traces/student.champsimtrace.xz -- \
    ./bin/telemetry_student --times 512 --devices 64 --seed 123 --pattern stress

Capture succeeds only after a complete ROI and successful driver verification. It writes the compressed trace, a .xz.json metadata file with roi_instructions, and a .xz.capture.log. The helper streams compression, so it does not require storing the large uncompressed trace. Use a new filename for each experiment; --force explicitly replaces a capture after a successful run.

The trace contains 8192 additional lookahead records after the original ROI. They prevent the simulator from ending early at EOF while fetching the last task instructions. Exclude them from the measurement length: use roi_instructions from the metadata, not the padded file's record count. Truncated captures or captures reaching the safety limit are rejected.

Run the two complete tasks, using their separate instruction lengths:

mkdir -p results
N_REFERENCE=$(python3 -c 'import json; print(json.load(open("traces/reference.champsimtrace.xz.json"))["roi_instructions"])')
N_STUDENT=$(python3 -c 'import json; print(json.load(open("traces/student.champsimtrace.xz.json"))["roi_instructions"])')

"$CHAMPSIM_ROOT/bin/champsim_part4" --warmup-instructions 0 \
    --simulation-instructions "$N_REFERENCE" --json results/reference.stats.json \
    traces/reference.champsimtrace.xz > results/reference.log

"$CHAMPSIM_ROOT/bin/champsim_part4" --warmup-instructions 0 \
    --simulation-instructions "$N_STUDENT" --json results/student.stats.json \
    traces/student.champsimtrace.xz > results/student.log

Confirm successful completion and a measured retired instruction count reaching the requested ROI length. There can be a small retirement-width overshoot. An incomplete run is not a final result. Starting implementations need not have identical instruction counts or IPC, and all compared runs must finish the same input and outputs.

You may reuse your reference capture and simulation across experiments when the fixed reference sources, compiler/version/flags, input, tracer/format, hardware and complete-ROI measurement method match. Keep its original metadata, binary/source provenance and logs. Regenerate the affected baseline when these conditions change.

Performance and Cache Statistics

Use the Simulation ROI in the native JSON. For the single core, read roi.cores[0].instructions and roi.cores[0].cycles. The task speedup is:

speedup = reference_cycles / optimized_cycles

The original implementation has speedup 1. Higher is better. This is a full-task cycle ratio; the Part 2 prefetcher IPC-ratio definition is a different comparison.

For every reported version, extract counters and calculate the following yourself:

  • ROI instruction length, measured retired instructions, cycles and task speedup.
  • L1D and L2C LOAD hits, LOAD misses, and LOAD miss rate. Read cpu0_L1D and cpu0_L2C; sum per-core arrays where present. Miss rate is misses / (hits + misses); report N/A for a zero denominator. Keep native miss counts, including merged misses.
  • DRAM read requests: sum RQ ROW_BUFFER_HIT + RQ ROW_BUFFER_MISS over the ROI's DRAM channels. These are memory-controller counts, not CPU LOAD counts.

Store raw counters and derived results in clearly labelled CSV files. Retain the native JSON and stdout logs. Prefetch Accuracy/Coverage are not required for this fixed-prefetcher program-optimization experiment. IPC, branch and TLB counters may support your analysis, but the performance score uses cycles.

Discuss absolute traffic as well as miss rates: a lower cache level may see fewer requests even when its local miss rate rises. Relate your intermediate working-set estimates to cache capacity, cache-line use and measured changes. Include the cost of packing or other extra work when interpreting a result.

Experiments and Report

Present the original implementation and at least two optimization versions, with a clear reason for each change. All final performance comparisons use the official medium input and complete-ROI method above.

For a parameterized choice, compare at least three settings while controlling the other changes. These settings can overlap your optimization-version runs. For an approach without tunable parameters, provide equivalent controlled comparisons or ablations. Explain both improvements and regressions, estimate the actively reused working set, and justify your final implementation using measurements.

Your report should make it possible to follow a change from code to access pattern, from access pattern to cache behavior, and from cache behavior to complete-task cycles. Use correctness-only inputs for debugging without treating their performance as the official result.
