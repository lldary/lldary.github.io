Archlab ChampSim Project 3

Part 2: Run Simulation with Prefetchers

ChampSim provides multiple classic cache prefetchers out of the box (located in the prefetcher/ directory). In ChampSim, prefetchers are assigned to a specific cache level (such as L1D, L2C, or LLC) directly in the JSON configuration file via the "prefetcher" key.

Note: Unlike simulators with dynamic Python scripting, changing the prefetcher module in ChampSim requires re-running ./config.sh and re-compiling the executable:

./config.sh lab3_config.json
make -j $(nproc)

Tip: You can set different "executable_name" values in your JSON file (e.g., "champsim_no_pf", "champsim_next_line", "champsim_ip_stride") to build distinct binary executables for different configurations without overwriting them.

In this part, we will explore three L1D prefetcher configurations (The L1I and L2C settings remain unchanged):

  • "no": Disables prefetching for baseline comparison.
  • "next_line": A simple prefetcher that fetches the contiguous next cache block on access.
  • "ip_stride": An Instruction Pointer (IP) based stride prefetcher that tracks strided memory access patterns per instruction.

ip_stride is attached to L1D. In the course implementation, it may choose to skip filling L1D when MSHR occupancy is high. The Accuracy and Coverage metrics below use L1D counters only; they do not measure all benefits of prefetches retained at lower levels. Interpret these local metrics together with IPC and Speedup.

Running the Simulations

Let's evaluate how these prefetchers impact system performance on two prefetch-sensitive workloads: shell_sort and gemm.

To run a simulation for a specific prefetcher binary, execute:

# Example: Running ip_stride prefetcher on shell_sort and gemm
mkdir -p results
./bin/champsim_ip_stride --warmup-instructions 20000000 --simulation-instructions 100000000 traces/shell_sort.champsimtrace.xz > results/ip_stride_sort.txt
./bin/champsim_ip_stride --warmup-instructions 20000000 --simulation-instructions 100000000 traces/gemm.champsimtrace.xz > results/ip_stride_gemm.txt

Repeat this process for the binaries compiled with "no" and "next_line".

Important note on simulation length and warmup

Hardware prefetchers rely on observing memory access patterns over time to train internal state tables. Setting the simulation or warmup instructions too low will result in inaccurate prefetcher accuracy and coverage statistics.

For final evaluations in Parts 2 and 3, use --warmup-instructions 20000000 (20M) and --simulation-instructions 100000000 (100M) on the same trace files and starting positions for every prefetcher. Collect statistics from the simulation phase only. You may use smaller instruction counts for debugging. Part 4 measures its complete analysis-function ROI with zero warmup and each implementation's own instruction length on the same hardware; see Part 4.

Analyzing Statistics

Use simulation-phase counters only. Warmup trains cache and predictor state, but its instructions, cycles, and events must not be included in the reported counters. Use the course version's measurement-phase statistics reset; do not reset predictor state at this boundary. Prefetches crossing the boundary follow that version's event-counting semantics, so Accuracy and Coverage are finite-window estimates.

The following names are normalized CSV fields, not assumed ChampSim output labels. Extract them from the CPU 0 and L1D statistics of the course-provided version, and retain the original logs:

FieldDefinition
instructionsCPU 0 retired instructions during measurement
cyclesCPU 0 cycles during measurement
issuedL1D prefetch requests accepted by the cache's prefetch interface, using the simulator's issued counter; exclude rejected attempts
usefulThe simulator's native L1D USEFUL counter: includes both hits consuming a prefetched line and demand merges into an outstanding prefetch originating from L1D
demand_missesSum of L1D LOAD and RFO miss counters; exclude PREFETCH, WRITE/WRITEBACK, and TRANSLATION

For demand_misses, use cache-access miss counts, not newly allocated MSHRs or lower-level transactions. A demand access counted as a miss by the simulator remains a miss even when it merges with an outstanding request; do not deduplicate these counts by address. Use the same access-type scope and counter mapping for all runs. The course framework must provide and document counters matching these definitions; if a field is unavailable, resolve the framework mapping rather than substituting zero or an unrelated statistic.

In this course version, USEFUL is not restricted to timely LOAD hits. It increases when an eligible access consumes a line marked as prefetched, and when a non-prefetch request merges into an outstanding prefetch originating from L1D. Such a merge can increment both USEFUL and the demand miss counter. The native USEFUL counter can also include consumption by writes, whereas demand_misses here includes only LOAD and RFO. Use the native counter as reported; do not replace it with an independently estimated count of timely hits.

Report four metrics:

  • IPC: instructions/cycles.
  • Accuracy: useful/issued.
  • Coverage estimate: useful/(useful+demand_misses).
  • Speedup: IPCpf​/IPCno​, using the same workload, platform, and instruction window. The no baseline has Speedup 1.

Accuracy and Coverage use the native L1D USEFUL event count. Coverage is a proxy based on that count and remaining LOAD/RFO misses; the numerator and miss count can overlap and have different access-type scopes. It is neither a timely-prefetch coverage fraction nor the fraction of baseline misses actually eliminated. Prefetching can also change cache pollution and execution timing. Interpret Accuracy and Coverage together with IPC and Speedup.

If an Accuracy or Coverage denominator is zero, report N/A. For no, always report Accuracy and Coverage as N/A; retain its zero issued and useful counters. Do not collect or submit a late-prefetch metric.
