Archlab ChampSim Project 3

Computer Architecture 2026fall Project 3

By Prof. Jie Zhang

Due: 23:59:00, December 17, 2026

In this project, we will explore the design and evaluation of hardware cache prefetchers in a modern computer system using the ChampSim simulator. First, you will learn how to configure ChampSim's cache hierarchy and integrate prefetchers into specific cache levels (e.g., L1D, L2C, or LLC). You will evaluate how cache parameters and prefetching techniques significantly impact overall system performance.

Part 1 uses two provided synthetic traces to study data cache capacity allocation and mapping conflicts while keeping L1I fixed. Parts 2 and 3 use application traces to evaluate prefetchers on the shared baseline platform.

You are required to read a recent computer architecture paper introducing the Hyperion prefetcher to understand the core principles, architecture, and tradeoffs involved in prefetcher design. In Part 3, you will evaluate your prefetcher’s performance and compare it against baseline prefetchers across the provided workload traces.

Analyzing Statistics

Extract these counters from CPU 0 and L1D in the course version's statistics output, and keep the original logs:

FieldMeaning
instructionsInstructions retired by CPU 0 during measurement
cyclesCycles used by CPU 0 during measurement
issuedL1D prefetch requests that the cache accepted and sent out
usefulPrefetch requests that actually helped (see below)
demand_missesReal LOAD and RFO accesses that missed in L1D

What useful counts. A prefetch is useful when its data is consumed before it is thrown away. The simulator's L1D counter adds one in two cases: an access hits a line that is still marked as prefetched, or a demand request arrives while the prefetch is still in flight and merges with it. In the second case, both useful and demand_misses can increase for the same access.

What demand_misses counts. Count miss events on real LOAD and RFO accesses only. Do not include prefetch requests, writes/writebacks or translations. A demand access that merges with an outstanding prefetch still counts as a miss in the simulator, so keep it: do not remove duplicates by address. Use the same counting rule for every run.

Report four metrics:

  • IPC: instructions/cycles.
  • Accuracy: useful/issued.
  • Coverage estimate: useful/(useful+demand_misses).
  • Speedup: IPCpf​/IPCno​, using the same workload, platform and instruction window. The no baseline has Speedup 1.

What Accuracy and Coverage tell you. Accuracy answers one question: of the prefetches the cache sent out, how many paid off? Coverage estimate answers another: compared with the demand misses that remain, how much traffic did prefetching cover? The second number is only an estimate. The simulator's useful count can also include consumption by writes, while demand_misses counts only LOAD and RFO, and a merged access can appear in both. So it is not an exact fraction of the misses that prefetching removed. Prefetching also changes cache pollution and execution timing. Read Accuracy and Coverage together with IPC and Speedup, never on their own.

If a denominator is zero, report N/A. For the no run, always report Accuracy and Coverage as N/A, but keep its zero issued and useful counters. Do not measure or submit a late-prefetch count.

Course ChampSim API

  • prefetcher_cache_operate() receives typed addresses, the PC, hit status, useful_prefetch, access type, and metadata. In the provided header, cache_hit is uint8_t; zero means miss and nonzero means hit. Return metadata_in when your design does not modify metadata.
  • Activation: the cache calls your callback only for access types in its prefetch_activate mask, and never for requests generated by the cache's own prefetcher. In the shared platform, L1D calls it on LOAD and PREFETCH, not on WRITE or RFO tag checks. Keep these platform settings unchanged.
  • addr and ip are champsim::address, not integer block indices. In the shared L1D baseline, addr is a physical data address; ip identifies the initiating instruction. Data addresses may contain byte-offset bits, so normalize them consistently for history and fill lookups. A request without an initiating demand PC can have a zero ip.
  • useful_prefetch is true only when an access hits a line brought in by a prefetch. The simulator's USEFUL counter also counts demand requests that merge with an in-flight prefetch, so the two are not identical; see Part 2.
  • type is the scoped access_type enum. Compare it with values such as access_type::LOAD, access_type::RFO, or access_type::PREFETCH.
  • prefetcher_cache_fill() reports the fill address, long set/way indices, a uint8_t prefetch flag, evicted address, and metadata. A nonzero prefetch flag identifies a prefetch fill as reported by the simulator. A bypass has way == intern_->NUM_WAY and a default-constructed evicted address; do not index per-way state for a bypass. Return the metadata to associate with the filled line.
  • intern_ points to the attached cache. Include cache.h in the implementation when accessing fields or methods such as intern_->NUM_WAY or intern_->get_mshr_occupancy_ratio().
  • prefetch_line(pf_addr, fill_this_level, metadata) takes a typed byte address and a boolean fill choice. true fills the attached cache (L1D here); false forwards the request through the lower hierarchy without filling L1D. The boolean is not a cache-level number. The return value only says the request entered the prefetch interface's queue; it does not guarantee a memory transaction or a later fill callback. Handle rejection when maintaining request state or implementing retries.
  • Optional callbacks: prefetcher_initialize() runs once during initialization; prefetcher_cycle_operate() runs once per attached-cache operate tick, after its main tag/fill work; prefetcher_final_stats() can print custom statistics. Declare and define any optional callback you use. The branch callback belongs to instruction-prefetcher use and is not needed for this L1D task.

Use the typed address helpers instead of passing a shifted integer as a byte address:

const champsim::block_number block{addr};
const champsim::page_number page{addr};
const uint64_t block_key = block.to<uint64_t>();
const uint64_t page_key = page.to<uint64_t>();
const uint64_t block_in_page =
    champsim::page_offset{addr}.to<uint64_t>() / BLOCK_SIZE;
const champsim::address line_addr{block};
const champsim::address next_line_addr{block + 1};

block_key and page_key are integer indices suitable for table keys; line_addr and next_line_addr are typed byte addresses suitable for prefetch_line(). Apply the same block normalization in operate and fill callbacks.

Timestamps and Predictor State

Use intern_->current_time as your only clock source. It is available in both operate and fill callbacks, shares the cache's timebase, and needs no extra state. Record it on every event and convert elapsed time to local cache cycles with intern_->clock_period:

const auto request_time = intern_->current_time;
// Store request_time in a module-owned table; retrieve it on the later event.
const auto elapsed_cycles =
    (intern_->current_time - request_time) / intern_->clock_period;

Do not use access counts, host wall-clock time, or a second timestamp source. Keep predictor tables and timing state continuous across the warmup/measurement boundary; ChampSim resets its native measurement counters itself. Track rejected requests, repeated accesses, fills, and stale entries consistently.

Exactly What the Program Computes

The input is stored in acquisition order [time][device][channel]:

input.data[(t * D + d) * 16 + c]

Start with x[0] = input. For each stage s = 0, 1, 2, 3, every device, every channel, and every time t >= 3*(s+1):

weighted = x[s][t,d,c] + 2*x[s][t-1,d,c]
         + 3*x[s][t-2,d,c] + 4*x[s][t-3,d,c]
value = weighted / 10
limit = 2400 - 100*s + 50*(c % 4)
x[s+1][t,d,c] = clamp(value, -limit, limit)

Use signed 64-bit accumulation. Division is integer division toward zero, and the result is clamped after every stage. You do not need to design this filter yourself: the supplied condition() primitive already implements it.

After four stages, only times 12 <= t < T are valid. Store every final filtered value at:

output.filtered[((t - 12) * D + d) * 16 + c]

Then, for each valid time, compute the risk of a device as the sum of the absolute values of its sixteen final readings. Its alert threshold is:

threshold[d] = 600*16 + (19*d) % (400*16)

A device is in alert when its risk is strictly greater than its threshold. For each group of up to sixteen devices, report the total risk, the number of devices in alert, and the maximum device risk. The last group may contain fewer devices. The report layout is [t-12][group], with ceil(D/16) groups. summarize() already does this part.

Appendix A: Introduction to Cache Prefetchers

In modern memory hierarchy, the penalty of cache misses can be extremely large. This motivates designers to reduce the cache miss rate. Typically, some workloads show predictable memory access patterns, like sequentially accessing an array (address sequence as A, A+1, ...). In such cases, a previous access can inform the CPU about the potential following accesses (e.g., A can lead to A+1). The cache prefetchers are designed for these scenarios, which extract the workloads' access patterns, and load the following data before the CPU explicitly accesses them, eliminating cache misses.

The simplest implementation of prefetcher is the "next-line prefetcher", as shown in Fig (a) below. When the CPU access a block (cacheline) A, the next-line prefetcher will load the next block A+1 to the cache. Note that in cache hierarchy, the access granularity will always be block (typically 64B), so there is no concept like "next-byte prefetcher".

However, next-line prefetcher cannot perform well on some workloads. As a simple example, some workloads access the memory in a strided pattern, such as A, A+2, A+4,... (here we have stride = 2). In such scenarios, next-line prefetcher will never prefetch the being-used data. To serve these workloads, "stride prefetcher", as shown in Fig (b), is proposed, which can learn the actual stride from the memory access history, and perform useful prefetches.

The "degree" denotes the depth of prefetching. For example, the next-line prefetcher has degree = 1, for it prefetches one line per issue. If it has larger degree, it can be named as "next-N-line prefetcher".

Metrics to evaluate prefetchers

Use the ChampSim metric definitions in Part 2: IPC, Accuracy, Coverage estimate, and Speedup relative to no. Collect only measurement-phase counters, retain raw logs and counters, and calculate the metrics yourself using the specified formulas. Accuracy and Coverage are N/A for the no-prefetch baseline and whenever their denominator is zero.

Coverage estimates how useful prefetches compare with useful prefetches plus remaining demand misses. It does not directly measure the fraction of baseline misses eliminated. Speedup measures the resulting execution-performance benefit.

Accuracy and coverage are the standard prefetcher metrics, and they trade off against each other. Neither is a performance score on its own, so judge them together with IPC and Speedup. More aggressive prefetching will fetch more addresses, whether useful or not. Many of the actual accesses can be covered by prefetches, but much useless data is also prefetched, thus, increasing the coverage but decreasing accuracy. More conservative prefetching may increase accuracy but decrease coverage.

With these metrics, we can compare between next-line prefetcher and stride prefetcher: stride prefetcher can have higher accuracy and coverage than next-line prefetcher under strided accesses, since next-line prefetcher cannot prefetch any useful data.

Appendix B: Hyperion Prefetcher Brief Description

In this appendix, we will briefly describe the concepts of delta prefetching and timely prefetch. Based on this information, we describe the Hyperion prefetcher. This appendix is reference material for custom prefetcher design, not a required implementation specification. If you choose to adapt Hyperion, the final section describes permitted simplifications.

Delta prefetching and local-delta prefetching

To introduce delta prefetching, let's first consider a workload that performs an "irregular" memory access pattern: A, A+1, A+3, A+4, A+6, .... The stride sequence of this stream is +1, +2, +1, +2, .... Patterns that vary their strides like this are called irregular patterns. A normal stride prefetcher (check Appendix A for details) cannot provide any coverage for irregular patterns, since it cannot learn enough confidence for any individual stride value.

Delta prefetching is proposed to handle these irregular patterns. Conceptually, a "delta" is the address difference of current demand access with any previous accesses, as shown in the left figure above. The principle of delta prefetching is to learn among all existing deltas and issue prefetch based on deltas with the highest confidence. As shown in the right figure, with +1, +2, +1, +2, ... pattern, a delta prefetcher can learn that +1 and +2 has same confidence. It can then prefetch both +1 and +2, increasing the coverage (though may decrease accuracy).

Similar to branch predictors, prefetchers can also learn deltas based on local contexts, such as access history of individual PCs, or history inside individual pages.

Timely prefetch

A prefetch must arrive before the demand access to provide a cache hit. An example is illustrated in the figure below. Timeliness is a design concept here, not a required measurement or grading metric. Late prefetch happens because fetching data from lower levels of memory hierarchy requires time. For example, under the simplest pattern +1, +1, +1, ..., if the access interval is less than the fetch latency, next-line prefetcher can only provide zero coverage because all prefetches will be late. The principle of timely prefetch is to take prefetch latency into consideration. As shown in the right figure, timely prefetches can provide enough coverage.

To find the best timely delta for prefetch, prefetchers can estimate the fetch latency from accesses and data fills. When a delta prefetcher records previous accesses, it will also record a timestamp of the access's arrival. When the data is filled into the cache (green part in the figure), the fetch latency can be estimated with current timestamp - arrival timestamp. Based on this information, when an access B arrives, the best delta d should meet the following constraints:

  • In histories, the access interval between A and A+d is larger than the fetch latency (+2 and +3 in the figure).
  • The d is the minimal delta that meet the above constraint (+2 < +3).

Once the best delta is learned, the prefetcher can issue timely prefetches.

Hyperion

Hyperion is a local-delta-based L1D prefetcher that generates timely prefetches to enhance both the accuracy and coverage. The figure below shows the overview of Hyperion's structure and methods.

Hyperion contains two kind of tables: history tables and delta tables. Each individual PC and page has its own history table and delta table. The history tables record the recent potential misses (demand miss and hit on prefetch) with its address and access timestamp. The delta tables record the recent occurred timely deltas. Each table has a total counter, and each delta has its local counter. These counters are used to calculate the confidence of deltas.

Three types of cache events can trigger Hyperion:

  1. When there is a demand miss, Hyperion first updates the history tables (both PC and Page) with the address and timestamp. If a table is full, it will evict the earliest history (i.e., FIFO eviction). Then, Hyperion find both the PC delta table and Page delta table for the delta with highest confidence, and prefetch with this delta. This find-prefetch cycle will perform 12 times.
  2. When there is a demand fill (i.e., filling the data required by demand miss to cache), Hyperion will find the demand miss on this filled address in the history tables. The latency can be estimated by lat = current - timestamp. Then, it will scan the history tables and learn the best delta. Then, it will update the delta tables with this learnt delta. If the delta is already recorded in the table, the total counter and its local counter are plused by 1. If the delta is not recorded, the old delta with lowest confidence will be evicted, and the counters are updated (new local counter is 1).
  3. When there is a hit on prefetched data, Hyperion can use the recorded fetch latency to learn deltas and update its tables, then update history and issue new prefetches. In ChampSim, keep request and fill timestamps in module-owned tables keyed by cache block; do not assume the prefetch queue retains completed requests. Use the course version's useful-prefetch indication when available, or maintain per-line prefetched state from fill, eviction, and demand-access events.

Tip

  • Use consistent block addresses: Normalize addresses from both prefetcher_cache_operate() and prefetcher_cache_fill() with champsim::block_number{addr}. Use its .to<uint64_t>() value as an integer table key. Convert a predicted block number to champsim::address before passing it to prefetch_line(); a block index is not a byte address. See the typed-address examples in Part 3.
  • Use consistent simulated time: Follow the timestamp guidance in Part 3. Compute request-to-fill latency using timestamps from the same simulated time source. An access counter is not a cycle counter. Preserve the first outstanding request timestamp when repeated accesses target the same block, and remove stale tracking entries on completion or eviction as appropriate.
  • Record more information: The Hyperion is a hardware prefetcher. To mitigate its usage of hardware resources, it records only necessary information. However, in your simulator, you can use much more memory. Feel free to record useful information to improve your prefetcher. The approaches Hyperion uses to mitigate hardware overheads are not necessary in your implementation. We've listed them in next section.
  • Explore prefetch degree: You may issue multiple predicted blocks per trigger and evaluate the resulting Accuracy, Coverage, and Speedup. Respect ChampSim's request acceptance and queue limits; increasing degree can increase traffic and cache pollution.
  • Use lower threshold: Hyperion uses 0.8 as the L1D prefetch confidence threshold to avoid L1D cache pollution. However, such high confidence may lead to low coverage. You can use lower confidence during testing.

Features that are not required to implement

For this ChampSim lab, focus on predictor behavior rather than reproducing Hyperion's physical storage layout. The following simplifications are permitted within the shared evaluation platform; they do not permit changing cache timing, queues, or memory-system limits:

  • Unified tables: As described, Hyperion records histories and deltas for both individual PCs and individual pages. However, this can lead to redundant records. To reduce the used hardware, Hyperion merges the actual entries of PC and page tables into unified history/delta tables, and only uses separate indexing tables. In your implementation, you can just use two separate tables.
  • Prefetch buffer: A separate Hyperion-style retry buffer is optional. Respect the return value of prefetch_line() in the course version: a rejected request must not be recorded as successfully issued. You may drop rejected predictions or defer them through prefetcher_cycle_operate() without changing the simulator's queue limits.
  • Timestamp and latency recording: Use module-owned tables to record request and fill timestamps rather than adding fields to cache blocks or MSHRs. Use one consistent simulated time source as described in Part 3.
  • Dynamic cache-level selection: Reproducing Hyperion's confidence-based choice of fill level is optional. Use the course version's prefetch_line() interface if your design selects a fill destination, while keeping the prefetcher attached to L1D and preserving the shared cache hierarchy.
  • Additional prediction on prefetch fill: You need not reproduce Hyperion's extra prediction trigger on a prefetch fill. In prefetcher_cache_fill(), the prefetch argument identifies prefetch fills in the interface shown in Part 3; you may still use this callback to maintain timestamps and per-line state.
