Archlab gem5 Project 1

Computer Architecture 2025fall Project 1

By Prof. Jie Zhang

Due: 11:59:59 pm, October 8, 2025

Nowadays, ChampSim has become a widely used trace-based simulation framework in the computer architecture research community, especially for studying cache hierarchies, branch predictors, and memory prefetching techniques. This project will introduce how to build and configure a computer architecture simulation framework using the ChampSim simulator. We will study how different processor components, cache configurations, branch predictors, and memory prefetchers can affect the overall performance of a computer system.

Please note that ChampSim simulations can be time-consuming, especially when using long traces or running a large number of configurations. Therefore, you are strongly encouraged to start the project as early as possible.

For your convenience, we have tried to minimize the difficulties of setting up ChampSim. However, some configuration and compilation steps may still be tricky. Whenever you encounter any problems during this project, please refer to the ChampSim documentation or contact the TAs via WeChat or e-mail. All the following instructions and configurations have been verified on Ubuntu 22.04 environments.

Setup: Install Toolchain and Compile gem5

Install environment

As a complicated software, gem5 requires several prerequisites to run properly. However, manually preparing the correct environment is very challenging. For your convenience, we provide a Docker image with correctly installed prerequisites. To use the image, you first need to install Docker. On Windows system, you can easily install it by installing Docker Desktop; on Linux system, you can install Docker following the documentation. You can use the following command to check your installation:

docker --version

# You'll see contents like the following:
Docker version 24.0.2, build cb74dfc

Docker install tips

On Windows system, pay particular attention to verifying whether WSL2 is already installed on your computer or whether Hyper-V functionality is enabled. Failure to do so may result in various unexpected issues during the installation process. We recommend using WSL2 to support Docker. You can verify if WSL2 is installed with the following command:

wsl --version
Once you've installed Docker, you can pull our image with the following command: 
docker pull chaselab/archlab

Note

If you can't connect to Docker Hub, you can also download the image archive from our PKU Disk and load it with the following command:

docker load -i archlab-image.tar

All the resources used in labs will be visible in the PKU Disk.

After pull (load) the image, you can find it by running the following command:

docker images

# you'll see contents like the following:
REPOSITORY         TAG           IMAGE ID       CREATED        SIZE
chaselab/archlab   latest        c028b12a3ac4   1 second ago   1.8GB

Note

If you prefer to install the prerequisites for gem5 manually, you can follow the commands listed below.

sudo apt-get update; sudo apt-get upgrade
# For Ubuntu 20.04
sudo apt install build-essential git m4 scons zlib1g zlib1g-dev libprotobuf-dev protobuf-compiler libprotoc-dev libgoogle-perftools-dev python3-dev python-is-python3 libboost-all-dev pkg-config

# For Ubuntu 18.04
sudo apt install build-essential git m4 scons zlib1g zlib1g-dev libprotobuf-dev protobuf-compiler libprotoc-dev libgoogle-perftools-dev python3-dev python libboost-all-dev pkg-config

After preparing the environment, you should clone the codes of gem5. We have provided a skeleton code which you can clone from its repo, or download the code package from PKU Disk and then extract the codes to a directory.

Code clone tips

On Windows system, please run the following command before cloning the code repository:

git config --global core.autocrlf false

This will prevent compilation issues caused by differences in line ending definitions between Windows and Linux.

Once you have the codes, you are able to compile gem5. If you are using Docker (if not you can skip this part), you need to firstly create a container to setup the environment. Also, you need to mount the code onto the container when you start it, so that you can read and modify the code files inside the container. The command is as follows:

docker run -it --name <container name> -v <local path>:<container path> chaselab/archlab /bin/bash
  • The -it option means to attach stdin, stdout and stderr to current terminal, so you can operate the container interactively.
  • The --name <container name> option specifies the name of the new container. It may be useful when you try to run other commands on the container, but it is rather optional, because you can always specify a container by its individual ID. You can see the IDs and names of all existing containers with this command: 
    docker ps -a

# you'll see contents like the following:
CONTAINER ID   IMAGE                  COMMAND       CREATED          STATUS                      PORTS     NAMES
43518d84eb29   chaselab/archlab       "/bin/bash"   14 seconds ago   Exited (0) 14 seconds ago             lab1
  • The -v <local path>:<container path> allows you to mount a local directory to a directory in the container. Here, you need to specify the local path as the path to your gem5 code, for example, C:\Users\myname\gem5. The container path can be simple, for example, /gem5. When you enter the container, you can see all the codes under container path. Please note that this option only accepts absolute paths, otherwise the contents in the directory will not be correctly mounted.
  • The first argument after the options is the image name, here is chaselab/archlab.
  • The second argument is the command you want to run upon container start. Here we use /bin/bash to start an interactive terminal.

Thus, filling up all the options and arguments makes the command look like this:

docker run -it --name lab1 -v C:\Users\myname\gem5:/gem5 chaselab/archlab /bin/bash

Server account

If you still cannot compile or cannot setup WSL and Docker Desktop, feel free to contact TA for a server account.

Docker command tips

After starting the container, you can run any commands in it. However, you need to know more docker commands when meeting other situations:

  • If you've closed the container by running exit and want to run the lab again, you do not need to create another container with docker run. Instead, you can use the following command to restart your container and attach stdin, stdout and stderr to your terminal: 
    docker start -ia <container ID/name>
    If you are using a Windows system, you can also launch the corresponding container directly from the graphical interface of the Docker Desktop software.
  • If you start the simulation and want to close the terminal while keeping gem5 running, you can type ctrl+p+q to stop the interactive evironment and return to your own terminal. Then, when you want to return to the container, you can use the following commands: 
    docker attach <container ID/name> # return to the original container terminal
docker exec -it <container ID/name> <command> # start a new container terminal
  • If you want to make accessing Docker feel similar to accessing a remote server, you can use the Dev Containers extension for VS Code (refer to Appendix). This allows you to directly access the running container through VS Code, and use VS Code to edit code and execute command-line commands.

Compile gem5

Once the container has started, or if you have manually prepared the environment, you can proceed to compile gem5. Please note that gem5 must be built on a Unix platform (e.g., Linux and MacOS). gem5 uses SCons to manage its compilation. In this lab, we'll compile for ARM ISA:

cd gem5
scons build/ARM/gem5.opt -j $(nproc) # use all your cores to compile

Compile tips

If you run scons to compile and are warned with Cannot find 'pre-commit' (messages like the following), you can ignore the message (press enter and then press y). This is only required for contributing to gem5 and will not prevent the compilation.

You're missing the pre-commit/commit-msg hooks. These hook help to ensure your
code follows gem5's style rules on git commit and your commit messages follow
our commit message requirements. This script will now install these hooks in
your .git/hooks/ directory.
Press enter to continue, or ctrl-c to abort:
 Cannot find 'pre-commit'. Please ensure all Python requirements are
installed. This can be done via 'pip install -r requirements.txt'.
It is strongly recommended you install the pre-commit hooks before working with gem5. Do you want to continue compilation (y/n)?

Building gem5 may take you more than 30 minutes on your PC. If it completes successfully, you will see the following results:

 [     CXX] ARM/base/date.cc -> .o
 [    LINK]  -> ARM/gem5.opt
scons: done building targets.

You now have a binary in the directory build/ARM called gem5.opt.

Part 1: Create and Run a Simple Configuration

ChampSim is a trace-based microarchitecture simulator widely used in computer architecture research. ChampSim focuses on simulating the processor microarchitecture and memory hierarchy. In this part, you will learn how to configure and run a simple ChampSim system, including the CPU core, cache hierarchy, branch predictor, memory hierarchy, and prefetcher.

Following the instructions in this part, you will build a basic ChampSim configuration and run it with a representative instruction trace. You will also learn how different processor and memory-system configurations can affect simulation performance.

Let's get started by creating a working directory for the project:

mkdir -p configs/proj1

ChampSim configurations are specified using JSON files. A configuration describes the major components of the simulated microarchitecture, including the CPU, instruction and data caches, branch predictor, prefetchers, and DRAM system.

For example, a simple configuration can be organized as follows:

{
  "executable_name": "simple",
  "block_size": 64,
  "page_size": 4096,

  "L1I": {
    "sets": 64,
    "ways": 8,
    "rq_size": 32,
    "wq_size": 32,
    "pq_size": 32,
    "mshr_size": 8,
    "latency": 4,
    "max_tag_check": 2,
    "max_fill": 2,
    "prefetcher": "no",
    "replacement": "lru"
  },

  "L1D": {
    "sets": 64,
    "ways": 8,
    "rq_size": 32,
    "wq_size": 32,
    "pq_size": 32,
    "mshr_size": 8,
    "latency": 4,
    "max_tag_check": 2,
    "max_fill": 2,
    "prefetcher": "no",
    "replacement": "lru"
  }
}

The exact configuration fields may vary depending on the ChampSim version used in this project. Please refer to the configuration files provided with the project for the supported parameters.

ChampSim executes a previously collected instruction trace and models how the instructions interact with the processor and memory hierarchy.

Selecting a CPU Model

ChampSim provides different processor configurations for evaluating microarchitectural behavior. The CPU model determines how instructions are fetched, decoded, scheduled, executed, and retired.

For this project, you will use the CPU configuration provided by the project repository. The CPU parameters can be adjusted when studying the impact of processor resources on overall performance.

Important parameters may include:

  • Instruction window size
  • ROB size
  • Load/store queue size
  • Number of execution ports
  • Dispatch width
  • Execute width
  • Retire width

These parameters allow you to study how different processor resources affect IPC and other performance metrics.

Configuring the Cache Hierarchy

The cache hierarchy is one of the most important components in ChampSim. A typical configuration contains:

  • L1 instruction cache (L1I)
  • L1 data cache (L1D)
  • L2 cache
  • LLC
  • DRAM

Each cache can be configured with different numbers of sets and ways, queue sizes, MSHR capacity, latency, replacement policy, and prefetcher.

For example, an L1 data cache may be configured as:

"L1D": {
  "sets": 64,
  "ways": 8,
  "rq_size": 32,
  "wq_size": 32,
  "pq_size": 32,
  "mshr_size": 8,
  "latency": 4,
  "prefetcher": "no",
  "replacement": "lru"
}

The number of sets and ways determines the cache capacity and associativity. The MSHR size limits the number of outstanding cache misses that can be tracked simultaneously.

Configuring Branch Prediction

Branch prediction is another important component of the ChampSim microarchitecture model. A branch predictor attempts to predict the target and direction of conditional branches before their actual outcomes are known.

For example, the configuration may specify:

"branch_predictor": "bimodal"

Different branch predictors can have significantly different prediction accuracy and performance. In later parts of the project, you will compare different branch prediction mechanisms and investigate workloads that are difficult to predict.

Configuring Memory

ChampSim models the memory hierarchy below the cache hierarchy, including the last-level cache and DRAM.

The memory subsystem can be configured with parameters such as:

  • DRAM capacity
  • Number of channels
  • Number of ranks
  • Number of banks
  • DRAM latency
  • Request queue size

Different memory configurations can significantly affect application performance, especially for memory-intensive workloads.

Running a Trace

ChampSim does not directly execute an application binary. Instead, ChampSim executes an instruction trace generated from a real program.

Therefore, you first need to obtain a trace:

mkdir -p traces

Place the provided trace files under the traces directory.

The exact trace format and trace-generation procedure depend on the ChampSim version and the traces provided with this project. You should use the traces distributed with the project unless otherwise specified.

Building ChampSim

After preparing the configuration, build ChampSim using the provided build system.

For example:

./config.sh configs/proj1/simple.json
make

After a successful build, the ChampSim executable will be generated according to the selected configuration.

If the project repository provides a wrapper script for configuration and compilation, please use the provided script instead of manually modifying the generated source files.

Running ChampSim

Once ChampSim has been compiled, run the simulator with the selected trace:

./bin/champsim --warmup_instructions 100000000 \
               --simulation_instructions 500000000 \
               traces/<trace-name>.champsimtrace.xz

The warmup period allows the cache hierarchy and branch predictor to reach a more representative state before performance statistics are collected.

The simulation period determines the number of instructions used for collecting the final performance statistics.

ChampSim will report statistics such as:

  • Instructions per cycle (IPC)
  • Branch prediction accuracy
  • Cache hit/miss statistics
  • MPKI
  • Memory bandwidth
  • DRAM statistics

For example, the output may contain information similar to:

CPU 0 cumulative IPC: 1.XX
CPU 0 branch MPKI: X.XX
CPU 0 L1D TOTAL ACCESS: XXXXX
CPU 0 L1D TOTAL MISS: XXXXX
CPU 0 L2 TOTAL ACCESS: XXXXX
CPU 0 L2 TOTAL MISS: XXXXX

The exact output format depends on the ChampSim version and configuration.

Experiment

After successfully running the baseline configuration, modify one microarchitectural component at a time and observe its impact on performance.

For example, you may change:

  1. L1 cache associativity
  2. L2 cache capacity

  5. Cache replacement policy

  7. Memory bandwidth
  8. Hardware prefetcher

For each configuration, record the IPC and other relevant performance metrics.

Part 2: Understand ChampSim Statistics and Output

After ChampSim simulation completes, it will print detailed simulation statistics to the standard output. You can redirect the output to a file for later analysis, for example:

./bin/champsim --warmup_instructions 100000000 \
               --simulation_instructions 500000000 \
               traces/<trace-name>.champsimtrace.xz \
               > result.txt

The output file contains detailed statistics generated from the ChampSim simulation. Specifically, it contains general information about the execution and performance of the simulated processor and memory hierarchy.

The exact statistics and output format may vary depending on the ChampSim version and configuration.

In this project, IPC and cache/memory statistics are important. IPC (instructions per cycle) is one of the most important performance metrics in ChampSim. You can directly obtain the IPC from the simulation output:

CPU 0 cumulative IPC: 1.XX

IPC can also be calculated from the number of simulated instructions and the number of simulated cycles:

IPC = simulated instructions / simulated cycles

A higher IPC generally indicates that the simulated processor can execute more instructions per cycle.

You can also use cache statistics to evaluate the behavior of the memory hierarchy. For example, the number of L1D accesses and misses can be used to calculate the L1D miss rate:

L1D miss rate = L1D total misses / L1D total accesses

Similarly, you can calculate the MPKI (misses per thousand instructions):

MPKI = cache misses / simulated instructions × 1000

These statistics are particularly important when studying cache configurations and hardware prefetchers. For example, a prefetcher may increase cache hits and reduce MPKI, but it may also introduce additional memory traffic. Therefore, you should consider multiple statistics when evaluating the effectiveness of a configuration.

You can use any finding approach (e.g., grep) to check specific statistics from the simulation output:

grep "cumulative IPC" result.txt
grep "L1D TOTAL" result.txt
grep "L2 TOTAL" result.txt
grep "branch MPKI" result.txt

This can be useful when running a large number of experiments, since you can automatically extract the statistics required for analysis.

Tip

You can redirect the output of ChampSim to a different file using standard shell redirection:

./bin/champsim --warmup_instructions 100000000 \
               --simulation_instructions 500000000 \
               traces/<trace-name>.champsimtrace.xz \
               > another-result.txt

You can also use tee if you want to see the output on the terminal while saving it to a file:

./bin/champsim --warmup_instructions 100000000 \
               --simulation_instructions 500000000 \
               traces/<trace-name>.champsimtrace.xz \
               | tee another-result.txt

This is important for this and other projects, because you may run many different configurations and traces during the experiments. Saving the output of each simulation separately can prevent previous experiment results from being accidentally overwritten.

For example:

mkdir -p results

./bin/champsim \
    --warmup_instructions 100000000 \
    --simulation_instructions 500000000 \
    traces/<trace-name>.champsimtrace.xz \
    > results/baseline.txt

You can then use a different output file for each configuration:

./bin/champsim ... > results/lru.txt
./bin/champsim ... > results/srrip.txt
./bin/champsim ... > results/prefetch.txt

Make sure to save important simulation results before running another experiment!

Part 3: Configure and Run ChampSim

In this project, you will run ChampSim with different configurations and workloads. Unlike gem5, ChampSim uses configuration files to specify the microarchitectural components of the simulated system. Therefore, instead of modifying a Python configuration script every time, you can prepare a configuration file and use it to build a corresponding ChampSim executable.

In this part, we will first go through the basic configuration, compilation, and execution process. You do not need to explore different CPU configurations in this part. The goal is simply to make sure that ChampSim can be configured, compiled, and executed correctly in your environment.

First, create a directory for this project:

mkdir -p configs/proj1

Then, create a simple configuration file:

touch configs/proj1/simple.json

The configuration file is a JSON file. It specifies the components and parameters of the simulated microarchitecture. For example, a basic configuration can contain an L1 instruction cache and an L1 data cache as follows:

{
  "executable_name": "simple",

  "L1I": {
    "sets": 64,
    "ways": 8,
    "mshr_size": 8,
    "prefetcher": "no",
    "replacement": "lru"
  },

  "L1D": {
    "sets": 64,
    "ways": 8,
    "mshr_size": 8,
    "prefetcher": "no",
    "replacement": "lru"
  }
}

Info

The exact configuration fields supported by ChampSim may vary between different versions. Please use the configuration format and parameters provided by the version of ChampSim included in this project.

After creating the configuration file, we can use it to generate a ChampSim executable:

./config.sh configs/proj1/simple.json

Then compile the generated configuration:

make

If everything goes well, the ChampSim executable should be generated successfully.

You can check the generated executable with:

ls bin/

For example, you may see:

simple

The exact executable name depends on the executable_name specified in the configuration file.

Running a Trace

Unlike gem5, which can directly execute a statically compiled application in SE mode, ChampSim is a trace-driven simulator. Therefore, you need an instruction trace as the workload.

For this project, the provided traces should be placed in the designated trace directory. For example:

mkdir -p traces

You can then run the generated ChampSim executable with a trace:

./bin/simple \
    --warmup_instructions 100000000 \
    --simulation_instructions 500000000 \
    traces/<trace-name>.champsimtrace.xz

The --warmup_instructions option specifies the number of instructions used to warm up the microarchitectural state, while --simulation_instructions specifies the number of instructions used for collecting performance statistics.

For the initial test in this part, you may use a relatively small number of instructions to quickly verify that the simulator works correctly:

./bin/simple \
    --warmup_instructions 1000000 \
    --simulation_instructions 10000000 \
    traces/<trace-name>.champsimtrace.xz

Once the basic workflow has been verified, you can use the longer simulation length specified by the project.

Tip

The first goal of this part is not to obtain meaningful performance results. Instead, you should make sure that all three steps work correctly:

  1. The configuration file can be successfully processed.
  2. ChampSim can be successfully compiled.
  3. The generated executable can successfully run an instruction trace and produce simulation statistics.

If any of these steps fails, please refer to the ChampSim documentation or contact the TAs before proceeding to the following parts.

Format issue (\r) with git and Windows

If you use Docker Desktop on a Windows system, you may meet a file format issue during compilation, especially when you clone the codes under Windows using git. git will automatically replace \n (LF) with \r\n (CRLF) for you. SCons may report the occurance of \r (or ^M) and throw an error. Here's three possible solutions:

  • Disable the auto replacement by git config --global core.autocrlf false, and clone (re-clone) the codes.
  • Use dos2unix under your container (you need to firstly install it using apt) to transform \r\n to \n. The command referring to this blog can be 
    find . -type f -print0 | xargs -0 dos2unix
  • Clone the codes inside container. Be careful, you will lose your codes when you remove the container if you choose this solution.

Run out of memory (SCons killed) issue

If you fail to compile and SCons reports message like the following, you are probably running out of memory:

collect2: fatal error: ld terminated with signal 9 [Killed]
# ... or
g++: fatal error: Killed signal terminated program cc1plus

As reference values, with 8 compile jobs (-j 8), the compilation and the link process ([LINK] -> build/ARM/gem5.opt) may both take up to 12GB memory. If your PC's physical memory is equal to or less than 16GB, you may probably meet this issue.

If you face this trouble, you can manually enlarge the swap space used by Docker container. On Windows, you need to firstly change the backend to WSL2 (installation method can be found in official doc). The setting process is like the following:

Next, stop Docker Desktop, and stop WSL by wsl --shutdown. Then, create a file named .wslconfig under C:\Users\Yourname, and write the following configs:

[wsl2]
memory=4GB
swap=32GB
autoMemoryReclaim=gradual

You can adjust the memory and swap values based on your PC's physical memory and disk space limits. WSL2 uses up to 50% of your physical memory by default. According to the memory usage values described above, the swap is recommended to be larger than 20GB. Set autoMemoryReclaim=gradual to save your physical memory when you are not running WSL or containers.

Lastly, start WSL, Docker Desktop and your container again. You can also start a new container by restricting its memory and swap limits:

docker run -it --memory 4G --memory-swap 20G -v ...

Remember to use the same <container path> in -v, otherwise compilation may fail. Or you can delete build/ and re-compile completely.
